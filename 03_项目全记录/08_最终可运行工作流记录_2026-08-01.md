## 一、最终结论

本次调试后，最终可运行版本不再采用原先的 6 节点全 JSON 严格输出方案，而是改为：

```text
开始
→ 信息采集
→ 公式计算
→ 风险判断
→ 方案生成
→ 结果输出
→ 结束
```

其中：

1. **信息采集**：大模型节点，负责从用户自然语言里抽取购买信息。
2. **公式计算**：Python 代码节点，负责校验数据与计算覆盖天数。
3. **风险判断**：大模型 Text 输出，负责生成风险判断文本。
4. **方案生成**：大模型 Text 输出，负责生成三种方案文本。
5. **结果输出**：大模型 Text 输出，负责整理最终用户回复。
6. **结束节点**：返回结果输出节点的最终文本。

原来的“输入校验”节点已从主链路中移除，避免大模型 JSON 严格格式校验导致工作流中断。输入校验逻辑已合并到 Python 代码节点中。

---

## 二、为什么调整

调试中发现，讯飞星辰工作流对大模型节点的 JSON 输出校验非常严格。如果大模型输出出现以下情况，工作流会直接报错：

```text
Workflow engine protocol validation failed
Node set output content does not match format
```

实际遇到的问题包括：

1. Boolean 字段被模型输出为空字符串。
2. Array 字段被模型输出为 `[]`，但平台字段设置不匹配。
3. 大模型节点输出 JSON 多字段时容易出现字段为空、类型不一致、格式不完全匹配。
4. 未使用但留在画布上的节点也会被平台校验，导致“未连接的边”报错。

因此最终采用更稳定的方案：

```text
代码节点负责结构化计算和校验；
大模型节点只输出 Text 文本；
后续节点通过单字段文本传递结果。
```

---

## 三、最终链路配置

```text
开始 → 信息采集 → 公式计算 → 风险判断 → 方案生成 → 结果输出 → 结束
```

需要注意：

- 不再保留“输入校验”节点。
- 如果画布里仍有“输入校验”节点，必须删除，不能只断开连线。
- 节点 4、节点 5、节点 6 都不要设置为多字段 JSON 输出。
- 节点 4、节点 5、节点 6 全部使用 Text 单字段输出。

## 五、节点 2：公式计算

### 节点类型

```text
代码 / Python
```

### 输入

逐字段引用节点 1 信息采集的输出：

```text
purchase_item：引用 → 信息采集 → purchase_item
price：引用 → 信息采集 → price
available_funds：引用 → 信息采集 → available_funds
avg_daily_spending：引用 → 信息采集 → avg_daily_spending
tracking_days：引用 → 信息采集 → tracking_days
substitute_item：引用 → 信息采集 → substitute_item
need_followup：引用 → 信息采集 → need_followup
followup_questions：引用 → 信息采集 → followup_questions
```

### 输出字段

只保留一个输出字段：

| 字段名 | 类型 | 说明 |
|---|---|---|
| calc_result | String | 公式计算结果，JSON 字符串，包含购买信息、校验结果、自由时间影响和覆盖天数变化 |

### Python 代码

```python
# -*- coding: utf-8 -*-
import json


def to_float(value):
    if value is None or value == "":
        return 0.0
    try:
        return float(value)
    except Exception:
        return 0.0


def main(**kwargs):
    data = kwargs

    purchase_item = data.get("purchase_item", "")
    price = data.get("price", "")
    available_funds = data.get("available_funds", "")
    avg_daily_spending = data.get("avg_daily_spending", "")
    tracking_days = data.get("tracking_days", "")
    substitute_item = data.get("substitute_item", "")
    need_followup = data.get("need_followup", "")
    followup_questions = data.get("followup_questions", "")

    price_num = to_float(price)
    available_funds_num = to_float(available_funds)
    avg_daily_spending_num = to_float(avg_daily_spending)
    tracking_days_num = to_float(tracking_days)

    validation_errors = []

    if price_num <= 0:
        validation_errors.append("价格缺失或不是大于0的数字")
    if available_funds_num <= 0:
        validation_errors.append("可支配资金缺失或不是大于0的数字")
    if avg_daily_spending_num <= 0:
        validation_errors.append("平均日花销缺失或不是大于0的数字")
    if tracking_days_num <= 0:
        validation_errors.append("记账天数缺失或不是大于0的数字")

    is_valid = len(validation_errors) == 0
    funds_insufficient = False

    if is_valid and price_num > available_funds_num:
        funds_insufficient = True
        validation_errors.append("商品价格大于当前可支配资金")

    ret = {
        "purchase_item": purchase_item,
        "price": price,
        "available_funds": available_funds,
        "avg_daily_spending": avg_daily_spending,
        "tracking_days": tracking_days,
        "substitute_item": substitute_item,
        "need_followup": need_followup,
        "followup_questions": followup_questions,
        "is_valid": is_valid,
        "funds_insufficient": funds_insufficient,
        "validation_message": "数据正常" if is_valid else "数据不完整或存在不合理项",
        "validation_errors": "；".join(validation_errors),
        "direct_cost_days": None,
        "before_coverage_days": None,
        "historical_total_spend": None,
        "after_avg_daily_spending": None,
        "after_coverage_days": None,
        "coverage_change_days": None
    }

    if is_valid and avg_daily_spending_num > 0 and tracking_days_num > 0:
        direct_cost_days = price_num / avg_daily_spending_num
        before_coverage_days = available_funds_num / avg_daily_spending_num
        historical_total_spend = avg_daily_spending_num * tracking_days_num
        after_avg_daily_spending = (historical_total_spend + price_num) / tracking_days_num

        ret["direct_cost_days"] = round(direct_cost_days)
        ret["before_coverage_days"] = round(before_coverage_days)
        ret["historical_total_spend"] = round(historical_total_spend)
        ret["after_avg_daily_spending"] = round(after_avg_daily_spending, 2)

        if not funds_insufficient:
            after_coverage_days = (available_funds_num - price_num) / after_avg_daily_spending
            coverage_change_days = before_coverage_days - after_coverage_days
            ret["after_coverage_days"] = round(after_coverage_days)
            ret["coverage_change_days"] = round(coverage_change_days)

    return {
        "calc_result": json.dumps(ret, ensure_ascii=False)
    }
```

### 预期核心结果

标准测试输入为：

```text

```


### 系统提示词

```text
你是风险判断器，只根据公式计算结果判断购买风险。

你会收到 calc_result，它是公式计算结果。

请输出一段中文文本，不要输出 JSON，不要输出 Markdown。

输出必须包含：
1. 风险等级：绿灯 / 黄灯 / 红灯 / 无法判断
2. 风险概括：一句话说明风险
3. 风险原因：结合购买前覆盖天数、购买后覆盖天数、减少天数说明
4. 风险标签：用中文分号隔开

判断规则：
- 如果数据无效，风险等级为“无法判断”
- 如果资金不足，风险等级为“红灯”
- 如果覆盖天数减少大于等于180天，风险等级为“红灯”
- 如果覆盖天数减少大于等于60天且小于180天，风险等级为“黄灯”
- 如果覆盖天数减少小于60天，风险等级为“绿灯”
- 如果记账天数小于30天，提醒“记账样本太少”
- 如果记账天数小于100天，提醒“平均日花销可能被短期消费扭曲”

禁止建议贷款、透支、分期硬买。
不要讲投资、收益、税务、法律、理财产品。
```

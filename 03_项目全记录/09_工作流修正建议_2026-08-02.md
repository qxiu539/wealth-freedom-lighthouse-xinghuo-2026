# 财富自由指南灯工作流修正建议

## 给队员的一句话

主分支的工作流已经可以跑通。当前需要先修正计算口径和验收结果，再继续做演示材料。现有 Python 代码把同一笔购买同时从现金中扣除，又加进日均花销，购买影响因此被算了两遍。

这份文件保留原有的《08_最终可运行工作流记录》，只提供修改位置、正确结果和复测步骤。

## 一、当前审查结论

### 已经完成的部分

- 已有信息采集、公式计算、风险判断、方案生成、结果输出五个主要环节和结束节点。
- 代码节点能处理缺失数字、资金不足和正常输入。
- 记录中保存了平台节点配置、提示词和演示输入，方便队员继续调试。

### 需要立即修正的部分

1. 购买后覆盖天数的公式重复计算购买价格。
2. 当前示例的 `after_coverage_days: 166`、`coverage_change_days: 209` 与工作流 v0.2 的确定性口径不一致。
3. 当前风险判断使用覆盖天数减少 60 天和 180 天的分档，这组阈值没有出现在此前确认的产品规则中，且会放大上面的公式误差。
4. 当前记录主要证明了节点配置和预期结果，仍需要补充平台真实运行结果或截图，才能把测试标为通过。
5. 当前六节点版本属于可运行的财务演示。证据型消费决策升级还缺少需求证据、替代证据、独立决策状态和后续复盘字段。

## 二、公式修正

### 当前代码的问题位置

在《08_最终可运行工作流记录_2026-08-01》的 Python 代码中，下面两步需要调整：

```python
after_avg_daily_spending = (historical_total_spend + price_num) / tracking_days_num
after_coverage_days = (available_funds_num - price_num) / after_avg_daily_spending
```

人话解释：买 6999 元的手机时，现金已经少了 6999 元。如果又把 6999 元摊进每天花销，系统会再扣一次这笔钱。

### 工作流应采用的核心公式

```python
direct_cost_days = price_num / avg_daily_spending_num
before_coverage_days = available_funds_num / avg_daily_spending_num
remaining_cash = available_funds_num - price_num
price_cash_ratio = price_num / available_funds_num

if price_num <= available_funds_num:
    after_coverage_days = remaining_cash / avg_daily_spending_num
    coverage_change_days = before_coverage_days - after_coverage_days
else:
    after_coverage_days = None
    coverage_change_days = None
```

购买后覆盖天数继续使用用户已经提供的平均日花销。`historical_total_spend` 可以作为说明字段保留，但不要再把它和计划价格合成新的核心日均花销。

如果未来要评估商品带来的持续性支出，应另外增加一个明确的持续支出输入，并单独命名为场景估算。一次性购买价格不能自动当作持续性日均花销。

### 6999 元案例的正确结果

输入：价格 6999 元、可支配资金 30000 元、平均日花销 80 元、记账 120 天。

```text
direct_cost_days = 6999 / 80 = 87.49，展示 87 天
before_coverage_days = 30000 / 80 = 375 天
remaining_cash = 30000 - 6999 = 23001 元
after_coverage_days = 23001 / 80 = 287.51，展示 288 天
coverage_change_days = 375 - 287.51 = 87.49，展示 87 天
price_cash_ratio = 6999 / 30000 = 23.3%
```

按当前建议灯号规则，这个案例应为黄灯。原记录中的 138.32、166 天和 209 天需要改成上面的结果。

## 三、灯号规则建议

先判断红灯，再判断黄灯，剩余情况为绿灯。判断使用未四舍五入的原始数字。

红灯条件满足一项即可：

- 价格高于可支配资金。
- 购买后覆盖天数少于 30 天。
- 价格占可支配资金比例大于等于 50%。

没有触发红灯时，黄灯条件满足一项即可：

- 购买后覆盖天数少于 90 天。
- 价格占可支配资金比例大于等于 20%。
- 记账天数少于 30 天。

其余情况为绿灯。记账天数在 30 至 99 天时，提示平均日花销可能受到短期消费影响；100 天及以上可按普通样本处理。

当前记录中的“覆盖天数减少大于等于 180 天为红灯、60 至 180 天为黄灯”建议删除。这个判断既没有在已确认的规则中固定，也会把公式错误放大后的结果继续传给风险节点。

灯号只说明当前现金安全垫受到的影响，不替用户决定买不买，也不评价商品价值。

## 四、战略层面的修改

当前工作流可以作为 v0.2 财务演示版本继续跑通。它还没有完成 v0.3 证据型消费决策升级。升级时建议按以下顺序搭建：

1. 先完成确定性财务计算，输出财务灯号。
2. 再收集当前问题、影响频率、最晚需要时间、预计使用频率和已有解决办法。
3. 记录至少一个替代方案及价格。缺少价格时显示待补充，不生成数字。
4. 将财务灯号与决策状态分开。决策状态使用 `ready_to_consider`、`gather_evidence`、`lower_budget_or_alternative` 三种状态之一。
5. 最终只给一个当天动作，并保留用户最后选择和后续复盘入口。

完整的 v0.3 设计稿已经放在队长交付包 PR #1 中。当前主分支的工作流记录可继续使用，等公式修正和测试证据补齐后，再按该设计增加字段与节点。

1. 把第二节的公式替换进 Python 代码节点，删除或停用 `after_avg_daily_spending` 对核心覆盖天数的影响。

遇到平台字段映射报错时，保留报错文字、节点名称和截图，再提交队员反馈。平台限制可以调整节点写法，不能自行改变公式和灯号阈值。

## 六、验收标准

本次修正完成后，应同时满足以下条件：

- 本地公式脚本全部通过。
- 6999 元案例得到 87 天直接成本、375 天购买前覆盖、23001 元剩余资金、288 天购买后覆盖、87 天变化和黄灯。
- 资金不足时不生成购买后覆盖天数，也不建议贷款或透支。
- 记账样本过短时明确提示，灯号最高为黄灯。
- 平台测试记录包含真实运行结果，不只写预期结果。
- v0.3 的新增字段与财务灯号分开记录，最终决定仍由用户作出。

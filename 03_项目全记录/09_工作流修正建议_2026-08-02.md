## 一、复核发现的问题

原 Python 代码存在五个会影响结果的问题：

1. 购买价格先从现金中扣除，又被加进日均花销，同一笔支出被计算两次。
2. 资金不足时仍保留 `is_valid: true` 和“数据正常”，后续节点可能继续生成普通购买方案。
3. 缺失输入没有确定的流程状态，风险、方案和最终输出节点仍可能继续运行。
4. 风险节点使用覆盖天数减少 60 天和 180 天分档，这组阈值没有进入已经确认的产品规则。
5. 原测试把 6999 元案例写成购买后覆盖 166 天、减少 209 天和红灯，结果与统一公式不符。

仓库还缺少修正版的平台运行证据。队员写过平台已调试至可以运行，这条记录只能证明当时的调试状态，无法证明本次修正已经在平台通过。

## 二、统一公式

```python
direct_cost_days = price_num / avg_daily_spending_num
before_coverage_days = available_funds_num / avg_daily_spending_num
remaining_cash = available_funds_num - price_num
price_cash_ratio = price_num / available_funds_num

if price_num <= available_funds_num:
    after_coverage_days = remaining_cash / avg_daily_spending_num
    coverage_change_days = before_coverage_days - after_coverage_days
else:
    after_coverage_days = None
    coverage_change_days = None
```

购买后覆盖天数继续使用用户提供的平均日花销。若以后要评估持续订阅、耗材或维护费，需要增加单独的持续支出字段，不能把一次性价格自动摊入日均花销。

展示取整统一采用正数四舍五入，0.5 向上取整。Python 和本地 JavaScript 验收脚本都显式实现该规则，避免语言默认取整方式不同。灯号判断始终使用取整前的原始数字。

记账天数必须为大于 0 的整数。20.5 天这类输入进入 `needs_input`，由系统要求用户重新填写。

## 三、三个流程状态

`needs_input` 表示必填数字缺失、无法解析、不是正数，或记账天数不是整数。此状态只输出最多 3 个补充问题，不计算灯号，不生成购买方案。

`funds_insufficient` 表示价格高于可支配资金。此状态固定红灯，不生成购买后覆盖天数，不建议贷款、透支、分期硬买或立即购买。

`normal` 表示输入完整且当前资金能够覆盖价格。此状态继续计算覆盖天数和灯号。

这三个状态由 Python 代码节点确定。后续大模型节点只解释结果，不重新计算，也不自行改变状态或灯号。

## 四、灯号规则

先判断红灯，再判断黄灯，剩余情况为绿灯。

红灯条件满足一项即可：

- 价格高于可支配资金。
- 购买后覆盖天数少于 30 天。
- 价格占可支配资金比例大于等于 50%。

没有触发红灯时，黄灯条件满足一项即可：

- 购买后覆盖天数少于 90 天。
- 价格占可支配资金比例大于等于 20%。
- 记账天数少于 30 天。

其余情况为绿灯。记账不足 30 天只会增加黄灯条件，不能覆盖红灯。30 至 99 天标记为中等样本，100 天及以上标记为高样本。

灯号只说明当前现金安全垫受到的影响，不替用户决定是否购买，也不评价商品价值。

## 五、6999 元案例

输入为价格 6999 元、可支配资金 30000 元、平均日花销 80 元、记账 120 天。

```text
direct_cost_days = 87
before_coverage_days = 375
remaining_cash = 23001
after_coverage_days = 288
coverage_change_days = 87
price_cash_ratio_pct = 23.3
sample_confidence = high
lamp = yellow
```

黄灯由价格占可支配资金 23.3% 触发。

## 六、战略边界

当前链路可以继续作为 v0.2 财务演示。它解决金额换算、现金安全垫提示和基础方案生成。

PR #1 中的 v0.3 设计增加需求证据、替代证据和独立决策状态。升级时应继续保持财务灯号与决策状态分离。财务灯号只来自公式，决策状态使用 `ready_to_consider`、`gather_evidence`、`lower_budget_or_alternative` 之一，最终决定由用户作出。

当前 PR 先关闭确定性计算和流程状态问题。平台复测通过后，再增加 v0.3 字段，避免同时修改计算底座和产品交互。

## 八、验收标准

- 6999 元案例输出 87 天直接成本、375 天购买前覆盖、23001 元剩余资金、288 天购买后覆盖、87 天变化和黄灯。
- 缺失或无效输入进入 `needs_input`，返回具体字段和补充问题，不生成方案。
- 资金不足进入 `funds_insufficient`，固定红灯，购买后覆盖天数为空。
- 短样本在没有红灯条件时触发黄灯；同时满足红灯条件时仍为红灯。
- 记账天数只接受正整数，平台 Python 与本地脚本采用相同的 0.5 向上取整规则。
- 平台测试记录包含真实输出、日志或截图，不能只填写预期结果。
